# Cloud Warehouse Migration Plan

## 1. Purpose

This document describes how the current local Home Credit risk decision-support system could be migrated into a cloud data warehouse environment such as Google BigQuery.

The current project uses local CSV files, generated reports, and JSONL audit logs. A production-style analytics environment would usually store scoring, audit, SHAP, analyst Q&A, and human review records in structured warehouse tables. This plan is a future-ready design document for data modelling, SQL analytics, auditability, data quality, governance, and cloud migration awareness.

This project is not currently deployed on Google Cloud or BigQuery, and it does not claim production banking deployment.

## 2. Current Local Architecture

Current local flow:

```text
raw Home Credit data
-> feature engineering
-> model-ready features
-> XGBoost scoring
-> SHAP explanation
-> FastAPI response
-> audit JSONL log
-> human review case
-> reviewer decision
-> analyst Q&A / LLM-assisted explanation
```

Current local artifacts include:

- `outputs/api_logs/scoring_audit_log.jsonl`
- `outputs/api_logs/human_review_cases.jsonl`
- `outputs/api_logs/human_review_decisions.jsonl`
- `outputs/risk_scores.csv`
- `outputs/sql_reports/`
- `outputs/agent_outputs/`

## 3. Why a Cloud Warehouse Layer Would Help

A cloud warehouse layer would make the project easier to analyze, monitor, and govern using standard data technology patterns.

Key benefits:

- SQL-based analysis across scoring, review, SHAP, and audit events.
- BI dashboard support for portfolio risk and reviewer workflow monitoring.
- Audit traceability from model score to review case and analyst decision.
- Model monitoring using score distributions, risk bands, and threshold flags.
- Data quality checks for missing features, unexpected features, and malformed logs.
- Reviewer workflow reporting by priority, status, reviewer, and decision type.
- Easier integration with cloud analytics tools such as BigQuery and Looker Studio.

## 4. Proposed Warehouse-Ready Tables

### A. `scoring_events`

One row per API scoring event.

Suggested fields:

| Field | Suggested Type | Purpose |
|---|---|---|
| `audit_log_id` | STRING | Primary scoring event identifier. |
| `timestamp_utc` | TIMESTAMP | Scoring event timestamp. |
| `endpoint_name` | STRING | API endpoint used for scoring. |
| `model_version` | STRING | Model version used for traceability. |
| `risk_score` | FLOAT64 | Predicted default risk score. |
| `risk_band` | STRING | Business risk band assigned to the score. |
| `threshold_used` | FLOAT64 | Candidate high-risk threshold used by the API. |
| `high_risk_flag_015` | INT64 | Candidate high-risk flag at threshold 0.15. |
| `missing_feature_count` | INT64 | Number of missing required model features. |
| `unexpected_feature_count` | INT64 | Number of unexpected input features ignored by the model. |
| `scoring_response_source` | STRING | Source of scoring response or request context, when available. |

### B. `shap_driver_events`

One row per local SHAP driver attached to a scoring event.

Suggested fields:

| Field | Suggested Type | Purpose |
|---|---|---|
| `shap_driver_id` | STRING | Unique SHAP driver event identifier. |
| `audit_log_id` | STRING | Links driver back to the scoring event. |
| `feature` | STRING | Feature name. |
| `feature_value` | FLOAT64 | Model input value for the feature when numeric. |
| `value_status` | STRING | Actual, sentinel missing, or special encoded value. |
| `shap_value` | FLOAT64 | Local SHAP contribution value. |
| `contribution_direction` | STRING | Positive or negative risk driver. |
| `contribution_rank` | INT64 | Rank within positive or negative driver list. |

### C. `human_review_cases`

One row per review case generated by the API governance layer.

Suggested fields:

| Field | Suggested Type | Purpose |
|---|---|---|
| `review_case_id` | STRING | Primary review case identifier. |
| `audit_log_id` | STRING | Links review case to scoring event. |
| `created_at_utc` | TIMESTAMP | Review case creation timestamp. |
| `status` | STRING | Original or current review case status. |
| `review_priority` | STRING | High, medium, or low review priority. |
| `review_reasons` | STRING | Review trigger reasons; could later be normalized. |
| `endpoint_name` | STRING | Endpoint that created the review case. |
| `model_version` | STRING | Model version used for the case. |
| `risk_score` | FLOAT64 | Risk score at case creation. |
| `risk_band` | STRING | Risk band at case creation. |

### D. `human_review_decisions`

One row per analyst decision event.

Suggested fields:

| Field | Suggested Type | Purpose |
|---|---|---|
| `review_decision_id` | STRING | Unique decision event identifier. |
| `review_case_id` | STRING | Links decision to review case. |
| `updated_at_utc` | TIMESTAMP | Decision timestamp. |
| `reviewer` | STRING | Reviewer or analyst identifier. |
| `review_status` | STRING | Review workflow status after decision. |
| `analyst_decision` | STRING | Analyst decision category. |
| `analyst_comment` | STRING | Analyst notes or rationale. |

### E. `analyst_qa_events`

One row per analyst Q&A request.

Suggested fields:

| Field | Suggested Type | Purpose |
|---|---|---|
| `qa_event_id` | STRING | Unique analyst Q&A event identifier. |
| `timestamp_utc` | TIMESTAMP | Q&A event timestamp. |
| `question` | STRING | Analyst question text. |
| `detected_intent` | STRING | Deterministic intent assigned to the question. |
| `answer_mode` | STRING | Deterministic or LLM-assisted answer mode. |
| `llm_enabled` | BOOL | Whether LLM generation was used successfully. |
| `llm_model` | STRING | LLM model attempted or used, when applicable. |
| `review_case_id` | STRING | Optional linked review case id. |
| `audit_log_id` | STRING | Optional linked scoring event id. |
| `retrieved_context_count` | INT64 | Number of retrieved documentation snippets. |
| `warnings_count` | INT64 | Number of warnings returned by the assistant. |

## 5. Table Relationships

Conceptual relationships:

- `scoring_events.audit_log_id` links to `human_review_cases.audit_log_id`.
- `human_review_cases.review_case_id` links to `human_review_decisions.review_case_id`.
- `scoring_events.audit_log_id` links to `shap_driver_events.audit_log_id`.
- `analyst_qa_events` can optionally link to `review_case_id` and `audit_log_id`.

Relationship diagram:

```text
scoring_events
  audit_log_id
      |
      +--> shap_driver_events.audit_log_id
      |
      +--> human_review_cases.audit_log_id
                 |
                 +--> human_review_decisions.review_case_id

analyst_qa_events
  optional audit_log_id ----> scoring_events.audit_log_id
  optional review_case_id --> human_review_cases.review_case_id
```

## 6. Example SQL Questions This Enables

Count applicants by risk band:

```sql
SELECT
  risk_band,
  COUNT(*) AS scoring_event_count,
  AVG(risk_score) AS avg_risk_score
FROM scoring_events
GROUP BY risk_band
ORDER BY risk_band;
```

Review queue volume by priority:

```sql
SELECT
  review_priority,
  COUNT(*) AS review_case_count
FROM human_review_cases
GROUP BY review_priority
ORDER BY review_priority;
```

Percentage of high-risk cases requiring review:

```sql
SELECT
  SAFE_DIVIDE(
    COUNTIF(h.review_case_id IS NOT NULL),
    COUNT(*)
  ) AS pct_high_risk_cases_with_review
FROM scoring_events s
LEFT JOIN human_review_cases h
  ON s.audit_log_id = h.audit_log_id
WHERE s.high_risk_flag_015 = 1;
```

Most common positive SHAP drivers:

```sql
SELECT
  feature,
  COUNT(*) AS driver_count,
  AVG(shap_value) AS avg_positive_shap_value
FROM shap_driver_events
WHERE contribution_direction LIKE 'positive%'
GROUP BY feature
ORDER BY driver_count DESC;
```

Analyst decisions by reviewer:

```sql
SELECT
  reviewer,
  analyst_decision,
  COUNT(*) AS decision_count
FROM human_review_decisions
GROUP BY reviewer, analyst_decision
ORDER BY reviewer, decision_count DESC;
```

High-score cases where analyst outcome was not automatic approval:

```sql
SELECT
  c.review_case_id,
  c.audit_log_id,
  c.risk_score,
  c.risk_band,
  d.analyst_decision,
  d.review_status,
  d.updated_at_utc
FROM human_review_cases c
JOIN human_review_decisions d
  ON c.review_case_id = d.review_case_id
WHERE c.risk_score >= 0.15
  AND LOWER(d.analyst_decision) NOT LIKE '%approval%'
ORDER BY c.risk_score DESC;
```

Cases with missing or unexpected API features:

```sql
SELECT
  audit_log_id,
  timestamp_utc,
  risk_score,
  risk_band,
  missing_feature_count,
  unexpected_feature_count
FROM scoring_events
WHERE missing_feature_count > 0
   OR unexpected_feature_count > 0
ORDER BY timestamp_utc DESC;
```

## 7. BigQuery Migration Approach

### Phase 1: Export Local Outputs

Export local JSONL and CSV outputs into flat structured files with stable field names. Validate that each JSONL record can be parsed and mapped to a target table.

### Phase 2: Create Warehouse Tables

Create BigQuery datasets and tables for scoring events, SHAP drivers, human review cases, human review decisions, and analyst Q&A events.

### Phase 3: Load Historical Local Files

Load existing local files into BigQuery tables. Reconcile row counts, null counts, and key relationships after each load.

### Phase 4: Build SQL Monitoring Views

Create SQL views for portfolio risk band trends, high-risk flag monitoring, review case volume, reviewer decisions, model version tracking, and input quality checks.

### Phase 5: Connect BI Tools

Optionally connect Looker Studio or similar BI tools to the warehouse views for dashboarding. Dashboard examples could include risk score distribution, review queue volume, common SHAP drivers, and feature missingness trends.

This plan does not implement Google Cloud code. It only documents a practical migration path.

## 8. Data Quality and Governance Considerations

Important controls for a warehouse-backed version:

- Define conceptual primary keys such as `audit_log_id`, `review_case_id`, `review_decision_id`, `shap_driver_id`, and `qa_event_id`.
- Use foreign-key style relationships even if the warehouse does not enforce them physically.
- Standardize timestamps in UTC.
- Persist `model_version` for every scoring, review, and Q&A event.
- Persist `threshold_used` to keep high-risk flag interpretation traceable.
- Track `missing_feature_count` and `unexpected_feature_count` for API input quality.
- Validate JSONL-to-table parsing with row counts and malformed-record checks.
- Reconcile audit trail completeness from scoring event to review case to decision.
- Preserve deterministic scoring evidence even when LLM-assisted answers are generated.
- Treat LLM output as analyst support, not as a replacement for model evidence or review decisions.

## 9. Limitations

- The project currently uses local files, not an actual cloud warehouse.
- BigQuery migration is a proposed future enhancement.
- No production authentication, access control, or data privacy controls are implemented.
- No real customer data is used.
- Local JSONL logs are useful for prototype traceability but are not a regulated audit system.
- LLM-assisted output is analyst support only, not automated credit approval.
- This design does not claim real bank deployment or production compliance readiness.
